# HTTPS sessions and search visibility

## Current session behavior

The API issues a 15-minute access JWT and a 30-day, rotating, HttpOnly refresh cookie. The frontend restores a same-tab session after reload, refreshes shortly before access expiry, retries one rejected guarded request, and clears account data on sign-out. The access token remains in per-tab `sessionStorage` so different staff roles can use separate tabs. A new tab remembers only the latest active role and session ID in localStorage, then restores that matching role cookie; it never stores either credential there. A new tab without the remembered identity starts as a guest. Deploy the matching backend change before the frontend because cookie-only new-tab refresh needs the updated resolver.

The production deployment must use one HTTPS origin for the site and GraphQL API. Confirm backend `.env` contains `CLIENT_URL=https://mnhospital.uz`, `AUTH_ALLOWED_ORIGINS=https://mnhospital.uz,https://www.mnhospital.uz`, and `BASE_URL=https://mnhospital.uz/backend`. Frontend `.env` must contain `NEXT_PUBLIC_API_URL=https://mnhospital.uz/backend` and `NEXT_PUBLIC_API_GRAPHQL_URL=https://mnhospital.uz/graphql`. Recreate the API container after backend environment changes; rebuild the frontend image after public environment changes. Do not print or paste refresh cookie values into chat or logs.

To verify a refresh in a browser, sign in over `https://mnhospital.uz`, reload, then open a new tab and confirm the same account returns. Keep a tab open for more than 15 minutes and reload a protected page; it should stay signed in. Sign out and open another tab: the private page must require sign-in. The regression harness is `npm run test:auth`.

## Search and link previews

Public pages have distinct server-rendered title, description, canonical URL, Open Graph/Twitter card metadata, and a public preview image. `_app.tsx` renders the shared `SeoHead` for every page, including staff workspaces and error pages. `_document.tsx` keeps the existing document, font and preference initialization only. Service, doctor and article directories and detail content come from their existing public GraphQL queries on the server. Detail metadata uses that same anonymous snapshot, avoiding a second metadata-only request. The preview image is `public/img/hospital-care-1.png`. Private account, booking, patient profile and staff pages are `noindex` and omitted from the sitemap. Preview service slugs keep their existing demonstration behavior and remain `noindex`.

Server reads never forward visitor cookies or authorization, so SSR does not populate likes/follows, mutate viewer counters or expose private workspaces. Existing authenticated Apollo reads, booking options, pricing and session restoration continue in the browser. A snapshot only fills its matching record/inquiry while fresh data loads; it does not replace the authenticated Apollo cache. Missing/unpublished detail records use the existing API's `No data is found!` response to return HTTP 404; malformed IDs also return 404. API outages return HTTP 503 with `Retry-After: 60`, preserving the existing recovery UI rather than declaring the record permanently missing.

`pages/robots.txt.tsx` points to `/sitemap.xml` using the same site URL as canonical links. The sitemap uses only public catalogs, reads the API's `metaCounter[0].total`, and requests deterministic ascending creation order. It retains already collected URLs on a later-page outage and uses a shorter cache for partial results. Static public URLs remain available if the API is down. One sitemap is capped at 50,000 URLs; introduce a sitemap index if the catalog grows beyond that limit. `NEXT_PUBLIC_SITE_URL` defaults to `https://mnhospital.uz`; `SEO_API_GRAPHQL_URL` optionally selects a server-side GraphQL endpoint. No language routes or unverified clinical claims are introduced; the existing EN/KR/UZ preference flow remains in place.

Run `npm run test:seo` for anonymous-read boundaries, indexing rules, missing/outage behavior and sitemap pagination/fallback. Against a running production build, run `SEO_VERIFY_BASE_URL=http://localhost:4202 npm run test:seo:http` to check initial HTML headings/links, metadata, private routes, HTTP 404 responses, robots and sitemap. The HTTP check uses real public catalog records and requires a reachable API with at least one record per catalog.

After deployment, check the HTML source for `og:image` and `rel=canonical`, and open `https://mnhospital.uz/robots.txt` and `https://mnhospital.uz/sitemap.xml`. In Google Search Console, verify ownership of the `mnhospital.uz` domain, submit the sitemap URL, inspect the home page and representative service, doctor and article URLs, then monitor indexing and Core Web Vitals. Search ranking is not guaranteed by metadata or a sitemap; useful original content, accurate clinic details, backlinks and site performance remain important. Add a verified street address and phone only when the business can substantiate them; do not fabricate local-business structured data.
